# 供用户确认的开发设计提纲

按任务复杂度选用以下结构与检查点，可合并或省略不适用项，无需为空章节凑字数。核心标准是：**用户能快速拍板确认，Agent 能据此无歧义实施**。

## 1. 推荐审阅结构（让用户一眼看懂）

在会话或设计文档中提交方案时，优先采用高信噪比结构：

| 模块 | 应交代清楚的核心内容 |
| --- | --- |
| **① 范围与可观察行为** | 本次做什么、面向什么角色、涉及哪些页面（如有）/接口/模块、明确不做什么 |
| **② 关键业务规则与功能约束** | 本次要改变哪些规则、必须保持哪些约束、约束的适用条件及依据，以及需求与现有行为的冲突处理 |
| **③ 技术实现与改动点** | 复用哪些既有组件/服务、新增或修改哪些核心类/接口/库表字段、数据如何流转、计算和转换分别由哪一层负责；额外机制有何必要依据 |
| **④ 验证与验收依据** | 如何验证约定变化及受影响的功能约束、用户交付后如何操作验收、已知环境限制 |
| **⑤ 待确认业务决策（如有）** | 仅列出无法从代码或材料推断的关键业务分歧，提供推荐选项及影响 |

优先选择能够完整满足需求、符合既有职责划分且引入额外机制最少的方案。只有存在实际取舍时才比较备选方案，无需为简单修改编造多套设计；未获需求或故障证据支持的优化可作为建议，不直接加入实施范围。

## 2. 需求常见隐含盲区（按需排查，不强行扩充需求）

原型截图通常只展示正常路径（Happy Path）的表面 UI，简短文字也可能省略业务规则。两种输入都结合当前功能按需排查以下高频缺口；纯文字需求无需补图，无页面任务无需设计页面（仅排查与本功能直接相关的项，不要无故给简单任务加戏）：

- **查询与列表**：模糊匹配还是精确匹配？默认排序规则是什么？分页还是全量？空数据或无权限时展示什么？
- **写操作与状态流转**：新增/修改的必填与唯一性校验？删除是逻辑删除还是物理删除？是否存在关联数据阻止删除？按钮是否需要防抖/幂等防重？
- **数据归属与权限隔离**：数据按个人、科室/部门、机构（orgId）还是租户隔离？不同角色看到的字段或可执行操作是否有差异？
- **跨服务与外部副作用**：是否涉及事务边界（如本地落库后发 MQ、调 Feign 远程接口）？下游失败时是阻断回滚、重试还是仅记录日志？
- **统计、导出与存量兼容**：统计口径的分母、时间范围与去重规则是什么？库表变更或状态调整是否需要兼容历史存量数据？

## 3. 提问与确认原则

- **优先利用已有证据**：有充分依据适用于当前业务场景、且与需求无冲突的项目约定直接沿用，并在设计中说明。已有同类实现只证明当前行为，不能自动确定新功能的权限、数据范围或其他业务规则。
- **带着依据与建议提问**：指出具体需求缺口、不同选择的业务影响及合理建议。形式和轮次按问题及宿主当前能力决定，不要求所有问题都变成选择题；新信息产生实质未知项时继续澄清。
- **阻断项分离**：范围中仍存在阻断性未知业务规则时，先把已知部分设计完整，明确标注待确认点，不把未知项直接当成定论开始写代码。
